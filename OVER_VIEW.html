oshihub · architecture

How the pieces actually connect

A file- and function-level map of the whole system: a Hono/Bun API that aggregates VTuber data from HoloDex, YouTube and Twitch into MongoDB, and oshihub, the Rust CLI/TUI that reads it. Every edge below was read out of the source, not inferred from the directory layout.

Read it top-down. Section 1 fits on a screen. Each section after it zooms into one box from the one before. If you only read one, read section 4 — the live path: it is the most correctness-sensitive code in the repo and the only part where two independent mechanisms write the same field.

01 System map

Three external APIs in, one Mongo Atlas database in the middle, one Rust binary out. Note that routes/ has two very different callers: the CLI (authenticated with a bearer token) and Twitch itself (unauthenticated, verified by HMAC instead).

external API runs on a timer HTTP ingress writes to Mongo storage client ··· dashed = inbound, we are called

The one asymmetry worth internalising. Twitch pushes (stream.online arrives in seconds); YouTube is polled (up to 5 minutes late). Everything downstream of that difference — the scheduler, the RSS edge-detection, the failed-poll guards — exists only because YouTube has no push equivalent.

02 Backend module graph

Every backend file and what it imports. Three modules are hubs — sync.ts, live-state.ts and models/ — and that concentration is deliberate: it is what stops two code paths from diverging into two implementations of the same write.

  • The mappers are an anti-corruption layer. No raw external response shape is ever stored. Every write goes through an explicit field mapping, so upstream schema drift breaks exactly one function instead of the database.
  • live-state.ts depends on nothing but the models. That is what lets both the Twitch webhook path and the YouTube poll path call into it without either knowing the other exists.
  • No import cycles. twitch-eventsub.ts imports sync.ts, never the reverse; routes/vtubers.ts is the only module importing both.

03 Boot sequence

index.ts top-to-bottom. Order matters more than it looks: the token check runs before anything binds a port, and the DB connect runs before the pollers that immediately query it.

  • No export default app. Bun's entry wrapper calls Bun.serve() on a default export that looks like a server config — and a Hono instance does, since it has fetch. With the explicit Bun.serve() below, that binds the port twice and dies with EADDRINUSE. bun run --hot skips the wrapper, so this only ever failed in the container.
  • idleTimeout: 120. Bun's 10s default measures socket silence, not request duration — it cannot tell a working handler from a vanished client. A forced sync fans out to three APIs and routinely runs past it, which surfaced as Caddy reporting 502.
  • Both pollers run an immediate cycle at boot, then self-reschedule only after the previous cycle settles — never a bare setInterval, so a slow cycle cannot overlap the next.

04 The live path

Two entirely independent mechanisms converge on two functions. This is the part of the system where a bug means a wrong notification, so it is worth knowing by heart.

The four rules that make this correct

  • A failed poll must change nothing. In the data, "the check failed" and "nobody is live" look identical — but only one of them means offline. Both populations skip their offline pass on a cycle where the poll itself failed, so a transient outage cannot mark everyone offline at once.
  • RSS is edge-detection only. A stream scrolls off the 15-entry feed window long before it ends, so "not in this cycle's RSS" never means "went offline". Anything currently believed live is re-checked directly through videos.list regardless of the feed.
  • markLive closes other live docs before upserting. A crash between the two steps leaves zero live docs rather than two. Zero self-heals on the next poll; two is the bug.
  • Verify HMAC over the raw body. JSON.parse then JSON.stringify does not reproduce the bytes, so the signature would never match. The callback reads c.req.text() and verifies before parsing.

Twitch's subscriptions are bound to the callback URL, not to a connection. That is why a local backend and the deployed one can now run simultaneously: both reconcile against the same shared subscription set pointing at PUBLIC_URL, and only production actually receives the webhook traffic. It is also why EVENTSUB_SECRET and PUBLIC_URL must be identical in both environments.

05 The sync path

All three syncFrom* functions share one skeleton: select tracked VTubers for this source, check two independent staleness gates, then run a live half and a stats half separately. The gates are the whole reason a 6-hour stats poller is cheap.

  • The two gates are independent. A VTuber can be due for a live refresh but not a stats snapshot, and the function does one without the other. ?force=true bypasses both.
  • Timestamps only advance on a successful HTTP call. A failed fetch leaves lastLiveSyncedAt untouched, so the next invocation retries rather than believing itself fresh — the same "a failure is not a negative result" principle as the live poller.
  • The stats poller runs every 6 hours against a 24-hour gate. Not a contradiction: the gate dedupes the extra ticks (a cycle where everyone is fresh is three DB reads and zero external calls), and the short tick bounds worst-case staleness after a container restart.
  • Registration fires a sync and does not await it. POST /api/vtubers resolves identity only; without the fire-and-forget syncFrom*(id, true), a new VTuber would sit with no streams or clips until someone synced by hand.

06 Data model

Four collections. Every content collection carries a sourceApi discriminator, and every one cascades from VTuber.

Indexes

CollectionIndexWhy
VTuber{ platform, platformChannelId } unique One record per channel per platform; the upsert identity.
Stream{ platform, externalId } unique The upsert key for every stream write. Makes sync idempotent.
Stream{ vtuberId, status } Covers markEnded's query and the stream-frequency aggregation.
Clip{ sourceApi, externalId } unique Keyed on sourceApi, not platform — a Twitch clip and a YouTube re-upload are different artifacts.
Clip{ vtuberId }Detail-view lookup.
StatSnapshot{ vtuberId, capturedAt: -1 } Time-series retrieval for the trend chart.

Three traps in this schema

  • Stream.url is not a stream identity. For Twitch it is twitch.tv/{login} — the same string for every stream that channel ever does. And startTime is rewritten whenever markLive re-upserts. Only externalId is both unique per stream and immutable, which is why oshihub watch keys on it.
  • A YouTube "Stream" is not necessarily a stream. The uploads playlist yields Shorts and ordinary videos too — 14 to 46 second "streams" have been observed on real channels. The duration-trend endpoint filters below 600 seconds and takes a median rather than a mean for exactly this reason.
  • Twitch has no view count. mapTwitchStatSnapshot stores follower count as subscriberCount and hardcodes viewCount: 0. Any chart summing view counts across platforms would be silently wrong.

07 CLI internals

main.rs is clap plus all output formatting; every network call funnels through routes.rs, and every client through config.rs.

The watch loop

  • apply() is pure and takes the poll result. That is what makes every rule testable with no network and no clock, and it is the seam a one-shot oshihub check would reuse.
  • Eviction takes two consecutive misses. It absorbs the window live-state.ts documents, where markLive has closed the old doc but not yet upserted the new one — a poll landing in between legitimately sees zero live docs.
  • external_client() exists deliberately. client() attaches the bearer token as a default header, which would ship our backend's shared secret to every CDN host we fetch an image from.
  • Polling, not SSE, and that is settled. This runs on a laptop: a pushed event fired while the lid is shut is gone, whereas the next poll returns current truth.

08 TUI message loop

Ratatui is immediate-mode: every tick throws away the last frame and redraws from current state. There is no incremental update to reason about, which is exactly what keeps ui.rs a pure function of &App.

  • handle_event never imports routes. It describes intent as a Command; dispatch in mod.rs is the one place that turns intent into a network call. That is what keeps event handling a plain synchronous mutator.
  • Two theme files, deliberately. theme.rs returns ColoredString, whose raw ANSI bytes render as literal text inside a ratatui buffer. The TUI needs ratatui::style::Style instead. They cannot merge — the convention is that a concept keeps the same colour in both, and both change together.
  • Images use ratatui-image, never viuer. viuer writes graphics escapes straight at the cursor, while ratatui repaints every cell each frame with no idea those cells are occupied. Each Protocol is baked at a fixed cell size, so ui.rs must render it into a Rect of exactly that size.
  • The TUI deliberately does not notify. oshihub watch takes no lock, so a terminal instance plus the systemd user unit already both fire; a third notifier would make it worse.

09 Endpoint reference

Auth is a single shared secret. /api/* and /sync/* require Authorization: Bearer <API_TOKEN> when one is set; /eventsub/* is exempt because Twitch cannot carry it, and relies on HMAC verification instead.

Method & pathAuthWhat it does
POST /api/vtubersbearer Register. Resolves source (HoloDex → YouTube fallback; Twitch always Helix), then fires an unawaited forced sync and, for Twitch, an EventSub subscribe. 409 if already registered.
GET /api/vtubersbearer List with optional platform, org, isTracked, name filters. Regex metacharacters in name are escaped.
GET /api/vtubers/livebearer Currently-live streams joined to their VTuber. Registered before /:id or "live" would be captured as an id.
GET /api/vtubers/:idbearer Detail plus the 10 newest streams, clips and snapshots.
GET /api/vtubers/:id/profile-urlbearer Browsable channel URL. Twitch needs a live Helix call — the stored id is numeric, not the login name a URL requires.
GET …/stats/stream-frequencybearer Dense bucketed counts. null = predates tracking, 0 = genuinely quiet.
GET …/stats/subscriber-trendbearer Sparse daily points; a missing day means "didn't sync", never "zero". Deltas are null when history is too short to answer honestly.
GET …/stats/duration-trendbearer Median seconds per bucket, floored at 600s to exclude Shorts.
PUT /api/vtubers/:idbearer Update name, englishName, photo, isTracked, org, suborg.
DELETE /api/vtubers/:idbearer Cascades to Stream, Clip, StatSnapshot; unsubscribes EventSub for Twitch.
POST /api/sync/{holodex,youtube,twitch}bearer Optional ?id= and ?force=true.
POST /api/sync/allbearer All three via allSettled — one source being down must not cost the other two.
